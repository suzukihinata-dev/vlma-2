# R2 設計メモ（段階0: 調査結果）

調査対象は GenesisGeo 固定版 22fe601 のソースと、R1 で生成した56件（`geometry.jsonl`）。確認できたことと、まだ確認していないことを分けて書く。

## 確認できたこと

### 生成データの形
1行のJSONLに `fl_problem`（作図言語の問題）、`llm_input_renamed`（`<problem>` 内に点ごとの前提と目標）、`llm_output_renamed`、`point_coords_grid`、`image_path` がある。`llm_output_renamed` は次のタグを持つ。

- `<aux>`: 補助点の作図。`x00 g : cong a c a g [008] ...`
- `<numerical_check>`: 数値的に成り立つ事実（`ncoll a c e [004]`、`sameclock ...`）
- `<trivial>`: 自明な事実（56件の例には無かった。他データでは出る）
- `<proof>`: 推論の手。`結論 [id] 規則名 [根拠のid ...]`。規則名は `r04`、`a00`/`a01`（代数的推論 AR）など。

例: `eqangle a b a c b e c e [005] AR [000] [002] ; cyclic a b c e [006] r04 [005] [004] ;`

### 再利用できる既存コード（車輪の再開発を避ける）
- `newclid.discovery.extraction.parsing.parse_proof_step`: 1手を `(結論述語, 引数, 結論id, 規則名, 根拠id列)` に分解する。`extract_tag_content`、`extract_goal` も使える。
- `newclid.evaluation.search_runtime.try_full_aux_dsl_to_constructions`: `<aux>` を作図言語に変換し、`Clause.parse_line` で構文検証する。R1 のモデル検証で動作確認済み。
- `newclid.evaluation.search_runtime.run_ddar_c` / `run_ddar_task`: 問題を DDAR で解く。
- `newclid.generation.writer.save_figure_as_png`、`draw_figure_task`: 図の描画。

### 操作語彙の写像
- `CONSTRUCT`: `<aux>` の各点の作図。
- `APPLY_THEOREM`: `<proof>` の各手（規則名、結論、根拠id）。

## 未確認・要判断

1. **手単位の検証の意味。** DDAR が検証するのは「問題から目標に到達できるか」であり、「この1手が規則 r04 の正しい適用か」を直接検証する API は見つけていない。段階1で実験して確かめる。当面の定義案: 手の結論が、問題＋これまでの作図から DDAR で導出できる（`Statement.check()` が真）ことを手の妥当性とする。規則名や根拠idの一致までは求めない。
2. **`<numerical_check>` と `<trivial>` の扱い。** 手として出力させる設計と、入力側の「情報」に含める設計がある。第一候補は後者（モデルに出させず、入力の情報欄に載せる）。理由は、これらは推論ではなく事実の注記であるため。
3. **作図の位置。** 現行データでは `<aux>` は証明の前に一括で出る。手ごとの形式では、作図を証明の手より前に並べる案が自然。作図を途中に挟むと、`<proof>` 内の根拠idとの対応が崩れる。
4. **点名の改名。** `_renamed` は点名を a, b, c... に振り直したもの。`point_coords_grid` はこの改名後の名前で持つ。手ごとの図の座標は改名後の名前に合わせる。
5. **56件の例は補助作図なしの短い証明（手数3）だった。** 作図手を含むデータでの確認は、段階1で補助作図を含む問題を生成して行う。

## 段階1の結果（2026-10-06、WNPC）

### 実験
- 生成: `scripts/r2_gen_probe.sh aux-small 20 --img 0`（`--n_clauses 10 --aux_only 2 --seed_cache`、4スレッド）。`--n_samples 20` の指定で**79件**が15秒で出力された（件数制御の問題は R1 と同じ。画像なし）。全79件に `<aux>`・`<numerical_check>`・`<proof>` があり、14件に `<trivial>` があった。証明の手数は11〜48手（中央値26）。R1 の既定設定の56件は補助作図が0件だったので、以降は `--aux_only 2` のデータで検証する。
- 再生: `scripts/r2_replay_probe.py`。`<aux>` を `try_full_aux_dsl_to_constructions` で作図に変換し、`fl_problem` の目標の前に足して DDAR（`GeometricSolverBuilder`）を実行。目標と、`<proof>` の各手の結論（`parse_proof_step` で分解し `Statement.from_tokens(...).check()` で確認）を調べた。

### 結果
| 実行方法 | 補助作図の変換 | 目標の証明 | 手の結論が成立 |
|---|---|---|---|
| 目標到達で停止（既定） | 79/79 | 79/79 | 2227/2240手（全手成立は73/79件） |
| 目標を外して飽和まで実行（`--saturate`） | 79/79 | 79/79 | **2240/2240手（79/79件）** |

- 既定実行で成立しなかった13手（6件）は、数値的には成立し（`check_numerical` が真）、乱数 seed を変えても同じ手が失敗した。飽和まで実行すると全て成立したため、原因は「DDAR が目標に到達した時点で止まり、元の証明が使った別経路の中間事実を導いていなかった」ことと判断する。
- 1件あたりの DDAR 実行時間は最大0.85秒。

### 設計への反映
- R2-1（操作系列の再生）: 79件では達成。全件の再生検証は、段階4で10万問に対して行う。
- R2-3（モデル出力の検証）: 手の検証は「問題＋それまでの作図に対して DDAR を飽和まで実行し、手の結論が成立するか」で行う。目標到達で止める方式では、正しい手を誤って不成立と判定する。これは結論の成立を見るもので、モデルが書いた規則名や根拠 id が正しいかは見ない（要件の解釈どおり）。
- 作図手の位置は「証明より前」で問題ない。`<aux>` の点を足した問題でも全手が再生できた。

### 限界
- 79件・10作図節以下の小規模データ。`--n_clauses` が大きい問題、補助点が2つの問題での確認は分けていない。
- 検証は結論の成立のみ。根拠 id が実際に結論を導くかは未検証。
- 作図の数値配置は乱数に依存する。段階3で図を出す際は、生成時の座標（`point_coords_grid`）との関係を確認する。

## 段階2の結果（2026-10-06）

### 実装（`vlma/` パッケージ。GenesisGeo のコンテナ内で実行）

### 設計上の訂正
- 完了の判定を「飽和状態で目標が成立」としていたのは誤り。飽和状態は証明の手を使う前から目標を含むため、作図の直後に完了になってしまう。実装は「受理した手の結論が目標と一致したとき」。
- 手の検証と完了の判定は別物。手は飽和状態での成立で見る。

### 限界
- 79件のみ。未使用の述語・規則（`aconst` など）はデータに現れた範囲しか確認していない。
- 完了の判定は、結論と目標の文が同じであることだけを見る。目標と同値な別の文を出しても完了にならない。
- 「情報」は `numerical_check` と `trivial`。ユーザーの発言「数値的な事実はいりません」の解釈（辺の長さを足さない）は未確認。
- 画像は最初の1枚だけ（`image`）。作図後の図は段階3で作る（`figure_index` が対応）。
- 負例は欄と却下理由の判定までで、負例のデータそのものは作っていない（R3 の前に決める）。

### 注意点
- 点が増えると図全体が縮尺されるため、前提の点の画像上の位置はターンごとに変わる。点の対応は位置ではなくラベルで取る。
- 図のラベルは大文字（A, B, ...）、操作文字列は小文字（a, b, ...）。GenesisGeo の既定のまま。
- 補助点の位置は、構成条件を満たす点の1つ。条件を満たす点が複数ある作図では、生成機が元々置いた位置とは別の位置になりうる。今回の79件では、`numerical_check` の事実との矛盾は出なかった（サンプルが少ないので、分岐のある作図が十分含まれていたかは未確認）。

## 図は補助情報として効くか（比較実験、2026-10-06）

### 方法（`scripts/r2_figure_ablation.py`）
- 公開モデル GenesisGeo-2B（R1 の vLLM サーバー）に、補助点を除いた問題（前提＋目標）を渡し、補助点を K=8 個提案させる。提案を問題に足して DDAR を実行し、目標が証明できるかを数える。
- 問題: `--aux_only 2 --max_auxiliary_points 1` で生成した300問のうち、補助点が1つの290問（補助点なしで解ける問題は0）。単一の補助点を1回提案する設定（深さ1）。
- リクエストは GenesisGeo 公式の `_build_vl_request_payload` / `_build_vl_text_request_payload` をそのまま使い、画像だけを差し替えた。サンプリングは公式と同じ（温度1.0、問題ごとに同じ乱数 seed）。
- 条件: 図あり（公式の描画）／白紙（同じ大きさの白い画像）／別問題の図（問題を1つずらして割り当て）／文字のみ（画像なし）。

### 結果（290問×8サンプル）
| 条件 | サンプル単位の成功率 | 8個のうち1個でも成功した問題 |
|---|---|---|
| 図あり | 71.0% | 239（82.4%） |
| 別問題の図 | 69.7% | 234（80.7%） |
| 白紙 | 62.6% | 221（76.2%） |
| 文字のみ | 62.2% | 224（77.2%） |

- 図あり − 白紙: 問題ごとの成功率の差の平均 +8.4 ポイント（95%信頼区間 +5.1〜+11.6）。問題単位では図ありのみ20、白紙のみ2（符号検定 p=0.0001）。
- 図あり − 文字のみ: +8.8 ポイント（+5.4〜+12.1）。図ありのみ16、文字のみ1（p=0.0003）。
- 図あり − 別問題の図: **+1.3 ポイント（−0.4〜+2.9）**。図ありのみ7、別問題のみ2（p=0.18）。差は有意ではない。

### 読み取れること
- このモデルは、画像が無い・白紙のときより、図らしい画像があるときに成績が良い。
- しかし、別の問題の図でもほぼ同じだけ成績が上がる。図の効果の大部分は、「この問題に固有の幾何学的な情報」を読んでいることではなく、「学習時と同じ種類の画像が入力にある」こと（分布の一致）で説明できる。この問題固有の情報の寄与は、今回の規模では検出できなかった（差はあっても約1ポイント以下）。
- 文字のみ・白紙の成績低下も、画像が無い入力がモデルにとって学習時と違う入力であることの影響を含みうる。

### 限界
- モデルは GenesisGeo の生成データと図で学習済み。問題も同じ生成機から作ったので、モデルの学習データと近い分布で、解答率は高い（図ありで82%）。訓練データとの重複は調べていない。
- 補助点が1つ・深さ1の設定のみ。補助点が複数ある問題、手ごとの規則適用（今回の APPLY の手）に対する図の効果は測っていない。
- 図ありの条件で、点が増えたあとの図（作図後の図）の効果は測っていない（今回は初期図のみ）。
- 公式のモデルは補助作図の提案だけを学習しており、R2 の形式（全手を出す）での図の効果ではない。

## 図の描き方の変種の比較（2026-10-07）

### 方法（`scripts/r2_figure_variants.py`）
前節と同じ290問・K=8・同じ乱数 seed で、図の描き方を変えた5種を比べた。各変種で「その問題の図」と「別問題の図」を渡し、DDAR で目標が証明できた割合と、両者の差（gap）を見る。gap は、問題固有の情報をモデルが使えている度合いの目安。
- official: 公式の描画
- annot_off: 長さ・角度などの印を描かない（生成機が出す印なし画像と同じ）
- lower_big: ラベルを小文字にして大きくする（操作文字列の表記と合わせる）
- zoom: 描画範囲を点の範囲に寄せる（大きな円が範囲を決めて点が小さくなるのを防ぐ）
- zoom_lower_big: 上の2つの組み合わせ

### 結果
| 変種 | その問題の図の成功率 | 別問題の図の成功率 | gap（95%信頼区間） | official との差（その問題の図） |
|---|---|---|---|---|
| official | 71.1% | 69.9% | +1.3（−0.4〜+2.9） | |
| annot_off | 69.8% | 68.3% | +1.5（+0.2〜+2.9） | −1.3（−3.2〜+0.6） |
| lower_big | 64.4% | 63.3% | +1.1（−0.6〜+2.8） | **−6.7（−9.5〜−3.9）** |
| zoom | 72.4% | 70.5% | +1.9（+0.2〜+3.6） | +1.3（−0.0〜+2.6） |
| zoom_lower_big | 67.5% | 67.8% | −0.3（−1.7〜+1.2） | **−3.6（−6.0〜−1.3）** |

official の gap と比べた各変種の gap の差は、いずれも信頼区間が0をまたぐ（−1.5〜+0.6 ポイント）。

### 読み取れること
- どの変種も、問題固有の情報をモデルが使う度合い（gap）を、official より有意に大きくはしなかった。gap は全変種で2ポイント以下。
- ラベルを小文字にして大きくすると、成功率が下がった（−6.7 ポイント）。モデルが学習時と違う見た目に弱いことを示す。したがって、このモデルでは、学習時と違う描き方の良し悪しは測れない。図が良くなっても、モデルが再学習なしでは読み取れない。
- zoom は成功率が +1.3 ポイントと最も良いが、有意ではない。
- この実験は、「図が問題固有の情報を持っていない」ことと、「情報はあるが、このモデルは読み方を学習していない」ことを区別できない。区別するには、図の描き方ごとにモデルを学習し直して比べる必要がある（R3 の範囲）。

### 判断
- R2 の図は、公式の描画（official）のままにする。生成機・推論時と同じ見た目で、学習済みの公開モデルとも整合する。
- zoom を R3 の比較候補に残す。R3 で自前のモデルを学習するときに、official と zoom を同じ条件で比べる。
- 実行時間: 5変種の逐次実行は13078秒（3.6時間）。クライアント側（DDAR と描画）が1コアで律速になる。以後の大きな比較は、変種ごとにプロセスを分ける。

## 段階4: 規模の測定とデータセット作成（2026-10-07）

### 追加した実装
- `scripts/r2_build_dataset.py`: 生成データから、重複除去 → 補助点の置き場所の決定 → 全手の検証 → 作図ごとの図の作成を行い、通った問題だけを `problems.jsonl`（コンパクトな形）と `figs/` に出力する。`rejected.jsonl` に却下された問題と理由、`stats.json` に件数・時間・容量を残す。`--limit` で件数を打ち切れる（生成機が要求より多く出す問題への対処）。
- `vlma/steps.py` に `to_compact` / `expand` を追加。1手ごとのサンプルは過去の操作列を毎ターン持つため、展開すると1問あたり約74KB（手数の2乗で増える）。保存はコンパクトな形（1問あたり約4.6KB）にして、読み込み時に `expand` で展開する。
- `vlma/figures.py`: `find_placement_seed`（補助点の置き場所の決定）を追加。`render_figure` は seed を受け取り、検証器と同じ seed で組み立てる。

### 検証中に見つかった問題と対処
1. **Python 版 DDAR は一部の問題で弱い。** 生成機が使う C++ 版と比べ、3点が一直線で `para` になる退化した配置（規則 r82）で導出できず、300問中12問で正しい手を却下した。C++ 版に切り替えると0件になった。
2. **C++ 版 DDAR は代数的推論（AR）で導いた角度の事実を、Python 側の状態に返さない。** 2000問中89問（すべて `APPLY AR : eqangle ...`）が却下された。→ 検証器は、2つの実装のどちらかで成立すれば受理する（`engine="both"`、既定）。
3. **補助点の置き場所が、生成機と食い違うことがあった。** 補助点が「2つの円の交点」など2通りに置ける作図で、生成機が選んだ側と再構築の側が逆になり、記録された向きの事実（`sameclock` など）が図で成り立たなかった（89問、4.5%）。生成機は補助点の座標を記録しない。→ 問題ごとに、記録された事実（`numerical_check`、`trivial`、各手の結論）がすべて数値的に成り立つ seed を探し（`find_placement_seed`）、`placement_seed` として保存する。図と検証は同じ seed を使う。2000問では、1884問が seed 0、89問が seed 3 で、見つからない問題は0だった。補助点が複数ある33問で、前の図の点が次の図で動くことはなかった。
4. **補助点の条件が3つ以上ある問題（1.35%）は、GenesisGeo 自身の変換関数が対応しない。** 公式の推論でも扱えない形なので、データセットから除く（`rejected_unsupported`）。

### 2000問での結果（`--n_clauses 10 --aux_only 2 --max_level 100 --seed_cache`、`--img 0`）
- 生成: 2000件を104秒（16スレッド）。`--n_samples 2000` で2000件ちょうど。20件の指定では79件、300件では300件だった。小さい値では要求より多く出る。

- 分布: 作図は1つが83%、2つが15%、3つが2%。手数は中央値52、90%点107、最大176（1問あたり平均59ターン）。手の約40%が AR、規則は36種。目標の述語は eqratio（38%）、eqangle、simtrir、simtri、perp など。

### 未解決の設計上の問題（要判断）
- **「情報」欄（`numerical_check`）が、推論時には作れない。** 学習データでは、証明が使う数値的な事実（`sameclock a b e b f d` など）だけが列挙されている。つまり、先の証明を知っているから選べる事実を、入力に含めている。推論時には証明が未知なので、同じものは用意できない。また、手の根拠の番号（`[008]` など）がこの事実を指すため、事実が文脈に無いと手が読めない。
- GenesisGeo では、これらの事実はモデルの出力（`<numerical_check>`）の一部。案: (A) GenesisGeo と同じく、モデルが数値的な事実を出力する（新しい操作 `CHECK` として、図で数値的に成り立つかを `check_numerical` で検証する）。(B) 図から機械的に求められる事実だけを入力に載せる。(C) 情報欄を空にする。

## 報酬の設計に向けた調査（2026-10-07）

ユーザーの決定: 最短の導出過程は強い報酬、無駄のある導出過程は弱い報酬、証明に必要ない過程は負の報酬。今のデータで何が作れるかを調べた。

### 分かったこと
1. **保存した証明では、全手が目標の導出に必要。** 10万問・6,803,430手のすべてで、各手の結論から根拠をたどると目標の導出に届く。目標に不要な手は0件（`scripts/r2_diag_cone.py`）。GenesisGeo の証明は、導出の全体から目標に必要な部分だけを抜き出したものだから。したがって、「証明に必要ない過程」は、今のデータには存在しない。
2. **導出の全体像（閉包）は、C++ 版 DDAR から取れる。** 1問あたり平均536件の事実と、それぞれの根拠が得られる。保存した証明は平均23.8手で、閉包の約4%。残りの約96%は、真だが目標に不要な事実。「証明に必要ない過程」は、ここから根拠つきで作れる。
3. **1つの事実につき、記録される導出は1つだけ。** 30問で、複数の導出が記録された事実は0件。DDAR は幅優先で導出し、最初に見つけた導出だけを残す。したがって、保存した証明は「DDAR が最初に見つけた導出」で、導出の深さでは最短だが、手数が最短とは限らない。別の導出経路（無駄のある導出）は、閉包からは得られない。
4. **手の根拠の番号は検証していない。** 手の「必要・不要」を、モデルが書いた根拠の番号をたどって判定すると、番号が間違っていれば判定も間違う。閉包の導出（DDAR 自身の記録）を基準にすれば、番号に頼らずに判定できる。

### 情報欄（案B）で未確定の点
- 「図から機械的に求められる事実」の範囲。真になる基本事実をすべて列挙すると、証明の結論になる事実が全部含まれ、答えが漏れる。漏れないのは、結論にならない種類（向きや非共線など、規則の適用条件になる事実）に限られる。
- 保存した手の `from` には、`numerical_check` の事実の番号が含まれている。案Bでは、これらの事実が入力に無いので、番号を `from` から外す必要がある（展開時に処理できる）。

## 情報欄（案B）の実装と、報酬の設計で見つかった検証器の抜け道（2026-10-07）

### 決定の反映（この全列挙方式は、下の「情報欄を追記方式に変更」で置き換えた）

### 検証器の抜け道（報酬を設計する前に直す必要がある）
- **作図のあとに目標の文をそのまま出すと、1手で受理され、完了になる。** 100問すべてで確認した（`scripts/r2_diag_shortcut.py`）。検証器は、手の結論が「DDAR の導出結果に含まれるか」だけを見るため。飽和した状態は、証明の手を使う前から目標を含んでいる。

## 情報欄を追記方式に変更、検証器の抜け道への対処、報酬の実装（2026-10-07）

### ユーザーの決定
1. 抜け道への対処は案2（書いた根拠の事実だけを前提に DDAR を実行して導けるか）。
2. 情報欄は、全てを並べるとコンテキストが溢れるので、適用した手に関わる点の長さと角度だけを、その手のあとに追記する（例: 三平方の定理を適用したら、その三辺と三角を追記）。

### 情報欄（追記方式、`vlma/info.py` の `InfoLog`）
- 手の結論に出てくる点（作図なら新しい点と、その条件に出てくる点）について、点どうしの長さと、3点の角度（頂点は真ん中の点）を、その手のあとに追記する。次のターンの入力から見える。累積し、同じ数値は繰り返さない。点が5個以上の手は長さだけ。座標は載せない。最初の手の入力では空。
- 長さ（先頭3000問・169,548サンプル）: 中央値906文字、90%点1871文字、最大3356文字。全列挙方式（中央値2410、90%点6386、最大20440）より大幅に短い。最後のターンでも中央値1115文字。
- 注意: 長さ・角度は、頂点が一直線の点では0度や180度になる。この値は残している。
- 入力のうち、一番大きくなるのは情報欄ではなく、過去の操作列（最大176手）と考えられる。操作列の長さは測っていない。

### 検証器（`vlma/verify.py`）の2段階の検証
1. 結論が真か（従来どおり、飽和した DDAR の導出結果に含まれるか。Python 版と C++ 版のどちらかで成立すればよい）。
2. **書いた根拠から導けるか（新規）。** 手の `from` の番号を、述べた事実（問題の前提、受理した作図の条件、受理した手の結論）に直し、その事実だけを前提に C++ 版 DDAR を **1段だけ** 実行して、結論が導けるかを見る。1段にして、複数段の推論を1手に押し込む近道を防ぐ。1回あたり約7ミリ秒。
- 新しい却下の理由: `invalid_citation`（まだ述べていない事実を根拠にした）、`not_derivable`（結論は真だが、書いた根拠から導けない）。
- **結果:** 作図のあとに目標の文を直接出す近道は、100問中0件の受理（以前は100問すべて）。保存した正しい証明は、850問（150 + 400 + 300、計36,843手）で全手が受理され、すべて「最短」と判定された。

### 検証器の誤却下を2つ直した
1. **定数を含む前提が読めなかった。** GenesisGeo の `parse_fact_segments` は、`rconst a b a c 1/2 [000]` のように定数（`1/2`）を引数に持つ事実を読み飛ばす。番号 `[000]` が台帳に入らず、それを根拠にした手が `invalid_citation` になり、後続の手が連鎖して却下された（400問中43問）。自前の解析 `parse_facts`（`vlma/actions.py`）に置き換えた。
2. **C++ 版 DDAR は `circle` を目標として導けない。** 結論が `circle` の手（199手、規則 r72）は、根拠が揃っていても導出が成立しなかった（400問中5問）。`circle` だけ、書いた根拠からの確認を省く（`NO_GOAL_CHECK`）。結論が真であることの確認は残る。目標が `circle` になる問題は、データに見当たらない。
- 補足: 図の座標（`figure_points`）は小数6桁に丸めてあり、これで DDAR を実行すると、数値の判定が変わって誤って導けなくなる手がある（一時的な測定で確認）。検証器は丸めていない座標を使うので影響しない。`figure_points` は、情報欄の元データとして使う。

### 報酬（`vlma/reward.py`）。値は仮
- 基準は保存した証明。導出全体の種類: `shortest`（目標に届き、却下も不要な手もなく、手数が参照以下）、`wasteful`（目標に届くが、そうでない）、`incomplete`（届かない）。
- 手ごとの報酬: 却下された手は `rejected`（−1.0）、受理された作図は0、受理された適用で参照証明の手は shortest なら `strong`（1.0）・wasteful なら `weak`（0.3）・incomplete なら0、必要でない手は `negative`（−0.3）。
- 「必要でない手」は、結論が参照証明にない、または既に述べた事実の言い直し。**参照証明にない手は、別の導出経路の手でも不要と判定される**（DDAR は1つの事実につき導出を1つしか記録せず、別経路は取れないため）。
- 値（1.0 / 0.3 / −0.3 / −1.0）と、「届かない導出は必要な手の報酬を0にする」ことは、ユーザーの指定がなく、仮に置いた。
- テスト41件成功（近道の却下、存在しない根拠の却下、言い直しの判定、報酬の各種類を含む）。

### まだやっていないこと
- 報酬を学習データ（`rejected` 欄）に反映していない。負例のデータ生成（DDAR の導出の全体から、真だが目標に不要な手を根拠つきで作る）は未実装。
- 10万問の全件を新しい検証器で再検証していない（850問の抽出のみ）。

## 規則名、演算子の記法、検査で見つけた間違い（2026-10-07）

### 規則名（`vlma/rules.py`、対応表は `docs/R2_RULE_NAMES.md`）
- ユーザーの提案: 規則を番号（r**）ではなく、三平方の定理のような名前で呼ぶ。
- 公式の名前は GenesisGeo の `rules.txt` と C++ 版の `DDAR/theorem.cpp` にある。使われている39種類の番号のうち、`rules.txt` に名前があるのは25種類（手の約35%）で、残りは C++ 版にある。
- 番号は一意でない: r110 と r111 は、結論の述語によって別の定理を指す。名前では区別できる。公式の名前が重複する組もある（r28 と r82 は、どちらも "Overlapping parallels"）。
- 手の出力: `APPLY Equal_distances_define_circumcenter : circle e d f h [010] from [002] [009]`。検証器は、表にない名前と、その規則が結論にできない述語の手を `unknown_rule` で却下する。テストは52件成功。
- **コスト:** 1手あたり59文字から81文字（約37%増）。最後のターンの過去の操作列は、中央値2,797文字から3,887文字、90%点6,501文字から8,754文字、最大11,183文字から15,033文字。

### 命名の検査で見つけた間違い
命名を「検査したか」と問われ、定義との照合をやり直して、次を見つけた。
1. **AR の3分類が間違っていた。** 最初は結論の述語から、角度（eqangle, para, perp, coll, constline）、長さ（cong）、比（eqratio, rconst）に分けた。C++ 版 DDAR が付ける理由で確かめると、coll と rconst は長さ（Dist）で、cong は長さ（Dist）と比（Distlog）の両方だった。約290問で確かめ直し、角度は eqangle・para・perp・constline、長さは cong・rconst・coll、比は eqratio・cong に直した。cong は両方で出るので、どちらの名前でも書ける。
2. **公式の名前が定義と合わないものがあった。** r109 は公式名が「比」だが、実際の前提は「等しい距離」。r72・r73・r108・r49・r50 も意味が取りにくく、定義（前提 ⇒ 結論）に合わせて名前を付け直した。
- 重複しないことは、コード（重複すると読み込み時にエラー）とテストで検査している。意味の照合は、公式の規則ファイルと C++ のソースを読んで手作業で行った。**規則名がその手に実際に使えるか（その規則だけで結論が導けるか）は、まだ検証していない。**

### 述語を演算子で書く案（導入しない）
- ユーザーの提案: ポピュラーな述語は演算子（`//` や `┴` など）で書く。
- 測定（GenesisGeo-2B のトークナイザー、300問・14,601手）: 記号は1トークン（`//`、`∥`、`⊥`、`┴`、`≅`、`∽`、`∠`、`△`）。ただし、1手あたりの平均トークン数は、現在37.0、`para`・`perp`・`cong` だけ演算子にして37.0〜37.1、全て演算子にして39.2（ASCII）〜41.2（Unicode）。述語名はもともと1〜2トークンで、`eqangle` を `∠(a b, c d) = ∠(e f, g h)` にすると括弧とカンマの分だけ増える。
- 事前学習の記法に近づくことによる効果は、測れていない。ユーザーの判断で、導入しない（現状維持）。
- なお、`┴` は罫線の文字（U+2534）で、数学の垂直記号（⊥、U+22A5）とは別。

## 規則名の検証と、全件の変換確認（2026-10-07）
